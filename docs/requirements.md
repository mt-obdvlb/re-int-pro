# T1 产品范围与验收

状态：2026-09-05 选题已由用户确认；本文件是实施前设计，不代表功能完成。项目代号 ProbeOps，正式题目为“基于竞争假设与探测成本的故障诊断 Agent”。实施顺序见 [实施计划](implementation-plan.md)。

## 目标、用户与演示

服务需要理解小型服务系统故障的开发者与学习者。输入是一个脱敏告警、服务名和观测窗口；输出是根因候选、可追溯证据、仍存在的竞争解释、停止原因与耗费。Agent 只读观测，故障注入由独立实验控制器执行。

典型演示：API 请求变慢，Agent 初始提出数据库连接池耗尽、缓存响应慢、后台队列积压三种解释；先读取成本较低且能区分候选的指标，再按结果读取特定 trace 或日志，最终定位或诚实返回“证据不足”。界面能展开每次探测的选择理由和被排除的解释。示例不预设实验效果。

项目的核心问题是：在相同模型和预算下，显式维护竞争解释并考虑探测成本，是否比固定流程和普通 ReAct 更有效？纯程序适合执行探测、权限控制和验收；Agent 负责不完整观测下的假设生成、预期现象与后续探测决策。

## 非功能要求与边界

- 默认单用户、仅监听 loopback；后端 8000、前端 5173，前端开发代理转发 `/api`。不做公开部署、账号系统、跨租户权限或生产诊断。本地绑定和 Origin 白名单须测试，不能直接将此模式对外暴露。
- 观测先固化为不可变快照再启动诊断。实验运行之间使用相同快照，消除故障演化带来的比较偏差；真实注入用于产生数据与演示，诊断本身不注入。
- 运行最多 12 次探测、16 次模型尝试（含重试）、180 秒、0.25 元；值可以降低，不允许通过请求突破上限。队列容量 20、运行并发 1；首版不承诺多机并行。
- 列表/状态接口目标 p95 <300ms，指本地测试、无模型等待的 100 次采样；只是验收目标。前端运行中每秒轮询，后台标签降至 5 秒；终态停止，错误退避上限 10 秒。
- 对断网、429、模型格式错误、工具超时、证据缺失均有明确状态。基础设施失败不能记作诊断“正确”，也不能静默从实验分母删去。
- 16GB Apple Silicon 机器使用轻量容器/进程，应用级故障注入优先；不把 Kubernetes、全量 AIOpsLab、训练、微调或多 Agent 协作列为必要条件。

## 前端页面与交互

| 页面 | 核心内容 | 必备交互状态 |
| --- | --- | --- |
| 任务与新建运行 | 脱敏告警、窗口、策略、限额、预计最大花费 | 空列表、加载失败、表单校验、预算不足；提交中禁重复点击并复用幂等键 |
| 运行列表 | 状态、策略、创建时间、费用 | 游标分页、空状态、错误重试；选中运行后进入详情 |
| 运行详情 | 状态条、竞争假设卡片、事件时间线、探测证据、日志追踪关联 | 轮询重连、取消待确认、终态、证据缺失、未定位；不能用绿色成功样式表现 failed |
| 诊断报告 | 结论、支持证据、替代解释、限制、成本 | 未完成返回冲突提示；failed/cancelled 仍可看事件，但没有伪造的最终报告 |

布局以桌面面试演示为主，支持键盘操作、清晰焦点、状态文字和颜色同时表达。三分钟演示顺序：告警→候选竞争→一次关键探测→报告/未知→追踪。首版不做复杂拖拽流程编辑器；图形仅展示服务依赖，不能将“相关边”呈现成已证明的因果边。

## 后续可选与明确舍弃

核心通过后才考虑 SSE、更多故障、第二模型稳定性检查。跨服务自动修复、任意 PromQL/SQL/shell、联网检索、用户上传日志、多租户、知识库平台和论文发表不在本次范围。扩展必须替换等量低价值工时，不能悄悄超过 300 小时。
