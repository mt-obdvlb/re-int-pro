## T1 ProbeOps：主动探测式故障诊断 Agent

对应理论：Lindley 信息量、ReAct、RCAgent、AIOpsLab；近邻包含 GALA 和诊断轨迹评价。具体来源见证据表 P01–P06。

### 三分钟项目介绍稿

老师好，我计划做的是一个主动探测式故障诊断 Agent。它面对的场景是，一个接口突然变慢，但超时并不直接告诉我们问题在哪里。原因可能是数据库连接池耗尽，也可能是队列积压，或者缓存访问延迟。如果只是把所有日志发给模型，让它写一份分析，模型很容易把最明显的异常当成根因，而且很难解释为什么查这些信息。

我想研究的核心问题是，在有限时间和调用预算下，下一步应该查什么。系统准备维护几个相互竞争的根因假设，每个假设都需要说清楚它预期看到什么证据。例如，连接池耗尽和慢查询都会让请求等待，但等待连接的时间与实际执行查询的时间应该不同。Agent 可以据此选择更有区分度的探测工具，而不是反复读取同一批报错。

在实现上，我准备搭建一个包含接口、任务服务、缓存和数据库的小型环境，通过可控故障注入获得独立标签。模型负责提出假设和选择探查动作，普通程序负责工具权限、时间窗口、预算限制和日志记录。每次返回的观测都会关联证据编号，让最终报告中的判断能够回到实际指标或日志。

这个设计的依据包括工具交互式推理和实验信息量的思想。不过，我不会把它说成新的诊断范式，因为自主根因分析、图引导调查和轨迹记录都已有研究。我准备验证的改进比较具体：按照竞争假设的分歧和探测成本选择工具，能否在相同预算下减少误判和无效调查。

最难的部分，我认为是让环境反馈真正约束模型，而不是让模型为自己的结论寻找解释。因此实验中，故障标签只给评测器，Agent 看不到注入脚本和答案。除了普通场景，还要加入不同根因产生相似症状、遥测缺失和未知故障，观察它会不会承认证据不足。

最后，我准备把方案与固定排障流程、普通 ReAct 和图引导基线比较，同时报告正确率、工具次数和费用。目前这些结果都还没有测量。这个项目希望体现的是，我能够把模型决策、系统观测和可复现实验连接起来，并解释一个判断到底依赖了什么证据。

### 八分钟深入讲述稿

老师好，我计划研究的是小型服务系统中的主动故障诊断。我想先用一个例子说明动机：用户提交任务时突然频繁超时，接口日志显示请求等待过久。这个现象并不能直接说明数据库坏了，因为队列处理太慢、数据库连接不足、缓存访问异常，都可能让上游接口出现相似表现。传统固定排障流程适合已知问题，但面对组合变化，往往需要先收集大量信息；直接让模型分析日志，又容易得到一段听起来合理却没有充分依据的解释。

我准备把诊断过程表示成一个不断更新的任务状态。状态中包括当前异常窗口、已经获得的证据、几个竞争性的根因假设，以及每个假设尚未被检查的关键条件。模型不会一开始就提交最终结论，而是先说明不同假设预期看到的现象。例如，数据库连接池耗尽时，获取连接的等待可能升高；如果只是某条查询慢，连接获取和执行阶段的时间分布可能不同。这些预期帮助系统决定下一次调查应该放在哪里。

随后，Agent 会从允许的工具中提出探测动作，例如读取某个时间窗口的连接指标、查看一次请求的调用链，或者检查队列长度。我准备根据这个动作预计能区分多少假设，以及执行和上下文成本，给它一个近似效用。这个思想来自信息量驱动的实验设计：一次观测的价值在于它能改变多少认识。不过，模型给出的预期不是经过校准的概率，所以实现中不会声称求出了最优信息增益，更不会给出没有依据的置信度百分比。

真正执行工具之前，程序会检查参数和权限，限制可访问的服务、日志时间窗口与返回规模。模型不能自由执行任意系统命令，也不能直接修改服务配置。工具返回后，原始结果保存在证据账本，模型上下文只保留有来源编号的摘要。这样既能控制上下文长度，也能在老师追问某个判断时展示依据。我还会区分空结果、超时与指标正常，因为没有读到日志并不代表系统没有发生异常。

在这个例子里，假设第一轮发现队列长度正常，那么队列积压的解释就应该被降低优先级，而不能被立即判成绝对不可能。第二轮如果发现等待连接时间很长，而真正执行查询的时间并没有升高，连接池相关问题就获得了更直接的支持。Agent 下一步可以查允许公开的配置和连接使用情况，而不是继续围绕慢查询展开。如果所有假设都无法解释新观测，系统应该重新提出候选，或者明确报告尚未定位，而不是硬选一个答案。

系统工程上，我准备把环境、工具网关、状态管理、模型决策和评测器拆开。环境负责运行小型服务及应用层故障注入；网关负责把不同遥测转换成统一结果；状态层负责保存证据和假设版本；决策层选择下一步行动；评测器只在最后读取诊断结果并与隐藏的故障标签比较。这样的拆分不仅为了模块清晰，也为了防止答案泄漏。例如，注入脚本名称和输出文件名里都不能出现根因，否则模型可能没有调查就猜中。

我会特别注意观测与因果的区别。一个指标和故障同时出现，不能自动证明它导致故障。最小项目中，Agent 只负责只读调查；如果要验证去掉某个因素后现象是否消失，只能由独立评测器在可恢复的实验副本中完成。最终报告需要区分直接观测、推测的传播关系和仍待验证的解释。对并发故障或者遥测采样不完整的情况，系统的结论也应相应收缩，不能因为报告写得完整就认为诊断正确。

理论上，ReAct 已经提供了推理与行动交替的基本范式，RCAgent 已经探索了自主工具诊断，AIOpsLab 提供了故障注入和评测设计，近期还有图引导调查工作。因此，我不会把这些已有能力算作自己的贡献。我的拟议改进是把竞争假设之间的可区分性和工具成本结合起来，并在同一个受控环境中测量这种选择是否有价值。最直接的反例就是：如果固定流程本来已经很短，新策略可能只增加模型调用成本。

实验准备包含固定排障、普通交互 Agent、图引导基线和完整方案，再去掉成本项或者改成随机探针做消融。所有方案使用同一模型、同一工具、同一任务信息和预算上限。我会同时比较根因位置与类型的正确率、工具次数、未知故障的误断言率和实际费用。相似故障不能只换一个随机种子就当成完全独立的数据，因此开发和封存集合需要按故障家族与参数组合隔离，重复运行则以任务为单位汇总。

范围上，我准备先把单故障的小环境做扎实，不把真实云平台自动运维作为承诺。如果主动选择探针没有带来提升，我会检查问题来自假设生成、工具观测不足，还是选择规则本身。这样的负面结果仍然能够形成有价值的边界分析。将来正式面试时，我会用真实轨迹展示一次成功定位和一次失败案例，并填写实际正确率与成本；在完成实验之前，我不会把计划描述成已经获得的成果。

### 五组追问与参考回答

**追问 1：为什么需要 Agent，普通排障脚本不能做吗？**

能，已知故障的短路径脚本通常更便宜，也应该作为基线。我考虑 Agent 的前提是，日志描述与故障组合会变化，下一步调查需要根据新证据调整。确定性的采集和权限检查仍交给脚本；如果实验发现脚本同样准确且成本更低，我会承认这个范围不需要更复杂的决策机制。

**追问 2：图引导和信息增益都已有研究，你的创新在哪里？**

我不准备把它们本身说成创新。拟验证的是，在同一个小型故障环境中，用当前假设的可区分性与工具成本共同决定下一步，比只沿依赖图调查是否更有效。这是有理论依据的受约束机制改进，需要和近邻方法比较；若行为与已有方法实质相同，就应定位为实现与复现，不声称独立新算法。

**追问 3：没有真实概率，怎么计算信息增益？**

严格的信息增益需要假设和观测的概率模型，当前方案不具备这个条件。我会使用预计能分开的假设对数作为近似分数，再除以归一化探测成本。它只是待验证的启发式，模型预测可能错，因此必须由真实观测更新，也要和随机、固定顺序进行消融比较。

**追问 4：如何排除只是调用模型更多带来的提升？**

我会统一模型、上下文可见信息和预算上限，并同时画实际成本与成功率的关系。只看相同最大步数还不够，因为一步调用可能长短不同。实验还会把额外调用成本记入总账，并检查在相近实际 token 开销下改进是否仍然存在。

**追问 5：最难的工程问题是什么，你个人要做什么？**

最难的是构造真实但不泄漏答案的故障反馈，以及让工具结果可以重放和核查。我计划承担环境、注入器、状态与证据账本、工具选择和对照评测；模型本身与参考框架必须注明来源。正式面试中，只有提交记录和运行证据支持的部分才能写入 `[本人实现部分]`。

## T2 ClarifySQL：证据与意图分流的 SQL Agent

对应理论与近邻：AmbiQT、AmbiSQL、信息增益式 SQL 澄清、SOMA-SQL、BIRD-INTERACT，见证据表 P07–P11。

### 三分钟项目介绍稿

老师好，我计划做一个能够区分数据证据与用户意图的 SQL Agent。它解决的问题不是单纯把中文翻译成 SQL，而是处理问题里没有说清楚的业务口径。例如，用户问上月有效订单的平均金额，数据库可能同时有创建时间、支付时间、退款状态和取消状态。即使模型写出的语句能够执行，也不代表它理解了用户想统计的订单。

我准备让系统先保留几个不同的解释，再判断这些解释之间的分歧可以通过什么方式解决。有些问题可以查数据库，比如状态字段实际有哪些取值；有些可以查已经提供的业务文档；还有一些必须问用户，比如这次分析是否包含退款订单。核心原则是，数据库里能查到一个结果，不能自动证明这个结果符合用户意图。

Agent 的作用是根据当前证据选择下一步：查看表结构、读取口径说明、执行受限的探针查询，或者提出一个有针对性的澄清问题。每次回答都会更新口径账本，最终 SQL 的关键条件都能对应到一个来源。执行权限、超时、返回行数和只读限制则由确定性程序控制。

这个题目有明确的已有研究基础。多解释 SQL、交互式澄清、信息增益提问和执行探针都已经有人研究，所以我不会把它们单独作为创新。准备验证的改进是，对歧义来源进行分流，能否在减少无效探测的同时，降低系统错误地替用户决定口径的概率。

实验中，我计划构建有隐藏意图契约的小型任务，由模拟用户只回答被问到的口径，不向 Agent 泄漏参考 SQL。然后比较一次生成、普通交互、信息增益提问、执行探针和完整分流方案。除了答案正确率，还要统计澄清次数、错误自信率和调用成本，防止一个系统靠不停追问提高准确率。

我觉得这个项目最值得讲的地方，是把自然语言的不确定性和数据库的精确执行放在一起。它可以展开关系代数、连接路径、空值语义、事务快照和信息获取策略。当前尚未实现，也没有效果数字；后续需要用真实对照证明，这种分流比简单流程更值得采用。

### 八分钟深入讲述稿

老师好，我计划做的项目是一个面向有歧义问题的数据库查询 Agent。我先举一个具体例子：用户希望统计上月有效订单的平均金额。对于程序来说，这句话至少包含几个没有确定的条件：上月按创建时间还是支付时间计算，有效是否排除取消和退款，平均值按订单还是按客户计算。如果系统直接写一条能执行的 SQL，很可能只是从多个合理解释中任意选了一个，结果看上去精确，但口径可能错了。

我的思路是先不要过早承诺唯一解释，而是保留少量语义不同的候选。这里的不同不是把表别名换一下，而是聚合粒度、过滤条件或连接路径不同。系统会把这些分歧记录成口径项，并标记当前依据来自哪里。这样后面的工具调用和用户澄清都有明确目标，不会只是让模型再想一遍。候选数量也要限制，否则组合爆炸会使每个问题都变成大量查询和长对话。

关键设计是把分歧分成三个来源。第一类是数据库可观测事实，例如某个字段的取值、是否存在重复记录；第二类是已有文档定义，例如公司明确规定有效订单必须支付完成；第三类是当前用户的分析意图，例如本次是否为了观察退款影响而保留退款订单。三类问题需要不同的信息渠道，不能因为数据工具方便调用，就让模型用数据分布替用户作决定。这个边界比“模型有没有信心”更容易检查。

在例子里，Agent 可以先读表结构和状态说明，确认支付时间字段可用。如果文档没有定义本次统计口径，它就应该问用户是否排除退款，而不是继续查十次状态分布。用户回答后，相关过滤条件从假设变成已确认口径，再生成和执行 SQL。最终结果除了数值，还会说明采用支付时间、排除哪些状态，以及这些条件来自哪次用户回答。老师追问某个条件时，可以直接回到那条记录。

选择动作时，我准备借鉴信息获取的思想，优先选择能解决较多候选分歧、但成本较低的动作。不过，信息增益式澄清已有直接研究，因此这不是我准备宣称的新算法。这里真正需要验证的是，加入歧义来源的判断后，系统会不会少做无法回答意图问题的探测，也会不会少问数据库本来就能回答的问题。模型可能把分歧分类错，所以分类错误必须作为失败类型单独统计。

执行层面，我准备使用只读数据库连接，并对语句结构、执行时长和结果规模作限制。仅仅检查语句以 SELECT 开头是不够的，因为复杂语句和函数也可能产生不符合预期的行为。候选查询还要在同一数据库快照上运行，否则两次查询之间数据变化，就可能被误认为是语义分歧。对于查询超时，系统应报告执行失败并调整查询，不能把超时当成这个业务解释不成立。

一个容易被忽略的问题是，两个 SQL 得到相同结果，不代表它们在语义上等价。比如当前月份没有退款记录，那么是否排除退款暂时不会改变均值，但到了下个月就可能不同。因此系统不会用一次执行相同来证明口径已经确定。反过来，结果不同也只说明解释有区别，并不能告诉我们哪个是用户想要的。这个例子可以把关系代数、实例上的执行结果和用户语义之间的区别讲清楚。

实验方面，我准备构建多个小型业务数据库，为每个问题提前写明隐藏的用户意图契约和参考答案。Agent 只能看到问题、允许的文档和工具。模拟用户只回答被明确询问的口径，不提供参考 SQL，也不暗示尚未被问到的过滤条件。开发集用于调提示和规则，封存集按数据库与问题模板分组，避免同一种问题换个名称就同时出现在两个集合中。公开交互式数据集可以作为外部参照，但只读子集不能冒充完整基准成绩。

我准备比较一次生成、普通 ReAct、信息增益提问、执行探针和完整分流，再去掉意图边界做消融。比较时使用相同候选集、模型、工具权限和总预算。如果一个基线本来能够向用户澄清，就不能为了让新方法显得更好而禁用这个能力。主指标是符合隐藏意图的答案正确率，同时报告提问次数、错误自信、无效探测和费用。还要单独看无歧义问题，防止系统把简单任务也变成繁琐问卷。

理论上，AmbiQT 提醒我们同一句话可能有多个 SQL，AmbiSQL 已经实现交互澄清，后续研究进一步加入信息增益和执行探针。因此这个项目应定位为受约束的机制改进与系统验证。我计划先支持小范围查询，不做完整商业 BI 平台。如果分流判断不可靠，或者简单规则就能达到相同效果，我会如实报告。将来面试中最有说服力的材料，应该是一条完整交互轨迹和一组公平对照，而不是“我接入了一个大模型”的功能介绍。

### 五组追问与参考回答

**追问 1：直接让用户填表确定口径，不就不需要 Agent 了吗？**

对于固定报表，填表完全可能更合适。我考虑的是问题结构、数据库和缺失条件会变化的场景，Agent 需要决定缺什么信息以及从哪里获取。如果所有任务都只是几个固定字段，项目就应该简化成确定性流程，不能为了叫 Agent 而强行加模型。

**追问 2：你和 AmbiSQL、SOMA-SQL 的区别是什么？**

它们分别覆盖交互澄清和执行探测等能力，因此这些都必须作为已有工作。我拟检验的是对证据来源进行分流，特别是限制用数据观测替代用户意图。它能否带来实质差异，需要在同等候选和预算下比较；如果只是换了提示写法且没有稳定效果，就不能声称新的方法贡献。

**追问 3：为什么数据库不能自动推断“有效订单”？**

数据可以支持某种解释，却未必唯一决定分析目的。例如数据库中取消订单很少，并不能推出用户本次一定要排除它们。只有明确的业务文档或本次用户回答，才能把这个条件变成已确认口径。系统可以提出建议，但应区分建议与已知事实。

**追问 4：如何证明不是因为多问了用户才更准确？**

我会同时看准确率和用户交互成本，设置相同的最大澄清轮数，并比较不同提问预算下的效果。还会统计问了却没有改变解释的问题。若提升仅来自更多提问，就应说交互机会增加有效，而不能把全部收益归因于分流机制。

**追问 5：最有工程含量的部分是什么？**

我计划重点实现语义候选账本、只读 SQL 网关和不泄漏答案的用户模拟器。难点是把口径、查询和证据对应起来，并区分语法错误、执行错误与意图错误。正式描述个人贡献时，需要展示 `[本人实现部分]` 的代码和测试，不把底层模型或第三方解析器算成自己开发的算法。

### 两条简历描述草案

- 拟开发具备歧义来源分流的只读 SQL Agent，结合数据库探测、文档检索与用户澄清，为查询条件保留可追溯依据。
- 拟构建隐藏意图契约与交互评测集，在统一预算下比较澄清和探测策略；完成后填写 `[意图匹配正确率]`、`[平均澄清次数]` 和 `[每题成本]`。

## T3 MemoryLedger：可追溯记忆与计划修订 Agent

对应理论与近邻：LongMemEval、Zep、MemState；官方 LongMemEval-V2 作为新近扩展参照。见证据表 P12–P14 及数据核查。

### 三分钟项目介绍稿

老师好，我计划做一个能够处理事实更正和计划修订的长期记忆 Agent。它面对的问题是，助手即使记住了新信息，也可能继续使用旧信息推出来的结论。例如，原来计划周五演示，因此周四冻结代码；后来演示改到周三，助手虽然更新了演示日期，却仍然建议周四完成冻结。这里出错的不只是某条记忆，而是事实与行动计划之间的依赖。

我准备让系统保存事件来源、适用时间和版本，同时记录派生建议依赖了哪些前提。某个前提发生变化后，相关建议先被标记为需要核查，再根据当前任务决定哪些必须重新计算。这样既不把所有历史全部丢弃，也不需要每次都把完整对话重新发给模型。

Agent 的作用主要在语义判断和选择性查证。它需要分清用户是在描述一个新变化，还是纠正过去说错的话；遇到不明确的范围时，要回读原文或请求澄清；准备给出当前计划时，要判断哪些受影响记忆与这次任务有关。图遍历、版本维护和事务更新等确定性工作，则由普通程序完成。

这个题目也有很接近的研究。长期记忆评测、双时态事实和依赖修订都已经存在，所以我不会把加时间戳或建立知识图谱称为创新。拟验证的改进是，在有限调用预算下，只重算当前任务会用到的受影响结论，能否比全量重建更省成本，又比只更新单条事实更少使用陈旧计划。

实验会使用有明确事件真值的虚构项目会话，并区分事实变化、历史查询、撤回、晚到事件和无关信息。不同方案使用相同模型和任务，包括完整历史、普通检索、时间感知更新和全量重建。评价不仅看回答是否正确，还看无关记忆有没有被错误修改，以及记忆写入和查询分别花了多少成本。

我觉得它适合展开缓存失效、增量计算、事件溯源、图结构和数据库一致性。当前方案还没有实现，最需要验证的风险是局部重算会不会漏掉重要依赖。如果为了省调用而频繁给出错误计划，那么这个改进就没有成立，必须如实说明。

### 八分钟深入讲述稿

老师好，我计划研究的是 Agent 长期记忆中的事实修订问题。我想从一个非常具体的场景出发：项目原定周五演示，所以助手根据规则安排周四冻结代码。后来用户说演示提前到周三，原来的周五安排作废。很多记忆系统可能成功检索到新日期，却仍然保留“周四冻结”的派生建议。这个错误说明，记录事实只是第一步，真正重要的是当前决策使用的前提是否仍然有效。

我准备把输入保留成不可随意覆盖的事件记录，再从事件中提取可查询的事实。每条事实至少关联原文、记录时间、实际适用时间和所属项目。这里要分清两个时间：系统什么时候听到这个消息，以及消息描述的事情什么时候有效。比如今天补充上周发生的变更，不能简单用今天的时间覆盖全部历史。保留这两个维度，才能同时回答当前安排和当时为什么作出那个安排。

对于派生结论，系统会保存它使用的前提编号和版本。例如冻结时间依赖演示日期以及提前一天冻结的项目规则。演示日期被更正后，程序沿反向依赖索引找出可能受影响的结论，先标记为待验证，而不是立即断言所有相关结论都错了。因为有些结论可能同时被其他证据支持，或者新的变化根本不适用于它所在的项目。影响传播是确定性图操作，语义是否适用则仍需要额外证据。

Agent 的决策出现在核查过程中。它会根据当前问题，决定先回读哪个原始事件，是否需要询问规则的适用范围，以及哪些待验证建议应该重算。在演示例子中，如果用户只是问当前冻结日期，系统没有必要重新整理全部历史聊天。但如果用户问上周制定计划的原因，就需要切换到当时有效的事实版本。模型负责理解这些自然语言区别，程序负责确保版本查询和状态写入遵守一致规则。

我准备特别区分变化和纠错。用户说现在改用方案乙，通常意味着方案甲曾经有效；用户说刚才说错了，应该一直是方案乙，则可能是在纠正先前记录。两种情况对历史问答和后续计划的影响不同。如果只是按最近一条记录覆盖，系统会丢失这种差异。因此，模型需要输出有来源支持的修订关系，遇到不明确的表达保留冲突或询问，不能凭时间新旧自动决定哪条事实更可信。

工程上，系统可以分为事件日志、事实版本库、依赖索引、任务检索和计划执行几个模块。事实与依赖变更要在事务中提交，避免事实已经更新，但旧的索引仍然被查询。重复输入通过事件标识去重，循环依赖则合并为待验证集合，并设置核查轮数上限。模型每次看到的是当前任务需要的片段和来源指针，原始证据仍可回读。最小版只操作虚构项目任务板，不连接真实日历，也不自动向他人发送消息。

理论和相关工作方面，LongMemEval 已经把更新、时间推理和拒答列为评测能力，Zep 已经实现时态记忆，后续 MemState 也讨论跨依赖修订。因此，我不能说自己首次解决了记忆失效。拟验证的范围更小：把当前任务相关性加入修订调度后，局部核查能不能以较低成本接近全量重建的正确性。这里的主要权衡是漏掉重要依赖与过度重算，不能只看检索命中率或节省了多少 tokens。

实验计划使用有明确事件模型的虚构项目序列。先定义事实、变更和规则，再写成自然语言会话，隐藏真值由事件模型产生，而不是让待测模型自己判断自己的答案。开发和封存集合按项目及事件模板隔离，并加入同名实体、不同项目日期相同、消息晚到、撤回后恢复和无关事实等情况。这样可以判断系统是否理解了适用范围，而不是仅靠“最近出现的日期”猜答案。公开长期记忆数据作为外部检查，但不会把改造数据的成绩冒充原始基准。

对照包括完整历史输入、普通检索记忆、时间感知单条更新、每次全量重建和完整局部方案，再移除任务相关性筛选做消融。所有方案使用相同模型，统一总上下文和动作预算。记忆写入成本必须记入总账，不能只展示查询便宜，却把前面大量总结和提取当作免费。评价重点是当前计划是否满足约束、是否引用陈旧前提、历史回答是否保真，以及有没有错误修改无关记忆。

这个项目与缓存失效和增量计算有很直接的联系，但也有区别：程序缓存通常有明确依赖，语言提取出来的依赖可能不完整。如果依赖漏检严重，全量重建反而可能更可靠，我会把这种情况作为结论而不是隐藏。如果最后场景被简化成完全结构化日历计算，普通程序就能解决，也不应夸大 Agent 必要性。我希望最终能展示一条事实更正前后的完整轨迹，并用真实实验说明局部修订在哪些条件下值得使用。

### 五组追问与参考回答

**追问 1：这不就是数据库加一张依赖表吗？为什么需要 Agent？**

存储和依赖传播确实可以由普通程序完成，这部分不需要模型。我考虑 Agent 的场景是事实来自自然语言，变化、纠错和适用范围并不总是明确，而且核查动作需要根据当前问题选择。如果输入已完全结构化、依赖也完整给定，那么数据库和规则引擎可能就足够了。

**追问 2：Zep 和 MemState 已经做了相关工作，你还能改什么？**

时间和依赖修订本身不属于我的新贡献。拟验证的是在有限预算内，把修订集中到当前任务将使用的受影响结论，并测量遗漏风险与成本的取舍。这属于受限场景下的机制改进，如果实验或代码核查发现与已有方法等价，就应该缩减创新声明，而不是换个名字。

**追问 3：为什么要保留旧事实，直接删除不是更简单？**

因为旧事实可能在过去确实有效，也可能解释当时的计划。直接删除会让历史问答和审计失去依据。我准备保留历史版本，控制它在什么时间和范围下能参与当前决策。保留并不意味着永远把全部历史发给模型，存储与上下文选择是两个不同问题。

**追问 4：怎样证明局部重算真的有效？**

需要同时和单条更新、全量重建比较。前者检验是否减少陈旧前提，后者检验是否省成本而没有明显牺牲正确性。还要统计无关记忆误改率，避免把大量更新误认为全面修复。若只报告回答准确率或 tokens 节省其中一项，证据是不完整的。

**追问 5：最困难的工程问题和个人贡献是什么？**

我认为是事实与派生索引的一致更新，以及对晚到、撤回和重复事件的正确处理。我计划实现事件存储、版本查询、影响集合和核查工具，并建立可重放测试。模型和已有图存储应清楚注明来源，正式面试只讲 `[本人实现部分]` 中自己能够解释并验证的内容。

### 两条简历描述草案

- 拟构建面向计划修订的记忆 Agent，以事件来源、事实版本与依赖索引支持更正后的选择性核查和历史回溯。
- 拟对比单条更新、全量重建与局部修订，分别核算摄入及查询成本；完成后填写 `[计划成功率]`、`[陈旧前提使用率]` 和 `[重算成本]`。

## T4 PatchArena：分歧驱动测试选择的代码修复 Agent

对应理论与近邻：SWE-agent、EvalPlus、测试与修复协同生成，以及实验辨别思想。见证据表 P01、P15–P17。

### 三分钟项目介绍稿

老师好，我计划做一个能够主动选择测试输入的代码修复 Agent。它关注的问题是，几个候选补丁可能都通过现有测试，但并不都符合完整规范。例如，一个区间合并函数出现错误，模型可能提出修改排序或修改端点判断等不同方案。普通重叠用例可能无法区分这些补丁，而边界相接、重复区间和空输入会暴露不同问题。

我想研究的是，在固定测试预算下，下一条测试应该测哪里。系统准备先生成少量候选补丁，再寻找这些候选输出不同的输入，把测试机会放在最可能改变选择结果的位置。Agent 可以根据反馈读取代码、修改候选或继续请求测试，形成真实的执行反馈闭环。

但候选有分歧并不意味着其中某一个一定正确。因此，期望结果不能由同一个模型随意生成，再拿来证明自己的补丁。最小项目准备使用规范明确的小函数，由独立参考实现或经确认的程序性质提供公开检查，并保留 Agent 看不到的隐藏测试进行最终评价。模型不允许修改规范和隐藏测试。

在工程上，我计划为每个候选准备隔离目录，限制可写文件和执行资源，并记录补丁、测试输入、结果与选择理由。超时、环境错误和语义错误需要分开处理。这样能够防止候选之间互相污染，也避免把关闭断言或吞掉异常当成成功修复。

这个方向已经有很多相关研究。SWE-agent 已经会操作代码和测试，EvalPlus 强调测试充分性，近期也有修复和复现测试共同生成的方法。因此拟验证的贡献不是自动写测试，而是在同一个候选池和预算下，分歧驱动的选择能否比随机输入和固定边界枚举更有效。

实验会报告隐藏测试上的完整修复率、错误补丁接受率、回归和实际费用，并用按母题隔离的任务检查泛化。我认为这个题目能自然联系算法边界、复杂度、差分测试和进程隔离。目前还没有实现或性能数字，如果候选都犯相同错误，主动找分歧就可能失效，这也是必须在面试中解释的限制。

### 八分钟深入讲述稿

老师好，我计划做的是一个面向小模块缺陷的代码修复 Agent，重点不在于一次生成更长的代码，而在于如何选择验证动作。我想用区间合并函数举例：规范要求合并闭区间，现有测试只包含普通交叠情况。某个补丁修改了排序，另一个补丁修改了端点相等时的比较规则，两者可能都通过已知测试。此时继续问模型哪个更好，得到的往往只是语言上的偏好；真正有用的是构造能区分它们的输入。

系统准备先读取规范、缺陷代码和可见测试，生成数量受限的候选补丁，再让模型提出可能区分候选的测试输入。程序会在隔离环境中运行这些候选，观察输出如何分组。如果所有输出相同，这个输入对候选选择的信息价值就较低；如果分成多个结果，则值得进一步检查。但我会明确区分“有区分度”和“有正确答案”，因为输出分歧只能暴露不一致，不能直接指出哪一个符合规范。

为了避免模型自我证明，公开测试的判定依据必须独立。对于规范明确的受控函数，可以使用事先确认的参考实现，或者人工验证过的程序性质。比如区间合并要保持覆盖集合不变，输出有序且不再有可合并区间。不过，几条性质未必完整刻画规范，因此最终还需要 Agent 无法读取的隐藏测试。生成补丁的模型不能修改参考实现，也不能通过查看隐藏用例来反复拟合答案。

Agent 的行动不只是挑选补丁。它需要根据失败反馈决定重新读哪段代码，是修正当前候选还是提出新的候选，以及是否还有值得测试的边界。例如，重复区间失败可能指向去重或更新逻辑，而长输入超时可能涉及算法复杂度。不同反馈要求不同操作，固定的生成一次再运行全部测试未必有效。不过，对于简单错误，固定流程可能更快，所以它也必须保留为实验基线，而不是先假设 Agent 一定有优势。

我准备使用一个成本敏感的选择规则，把候选输出的分组程度与执行开销结合起来，优先测试能较便宜地区分候选的输入。这与实验设计中的信息获取思想有关，但实现不具备完整概率模型，所以不会声称得到最优策略。它还必须保留部分规范边界检查，因为所有候选可能共享同一种错误。如果只寻找分歧，几个一致的错误补丁反而可能被误认为很可靠，这会成为专门的失败用例。

系统工程上，每个候选都需要独立工作目录，防止上一个补丁残留影响下一个结果。执行层会限制网络、可写路径、处理器时间、内存和输出大小；模型只能通过受控工具读取文件、提交局部补丁和运行公开检查。隐藏测试与评分程序放在 Agent 工作区之外。日志会记录每次执行对应的代码版本，这样一次测试通过才能和实际补丁关联，不能只看到绿色结果，却不知道运行的是哪个文件。

另一个难点是错误分类。依赖未安装导致测试无法启动，与补丁功能错误不是一回事；随机性导致的偶发失败，也不能直接当成稳定的修复证据。我计划先把环境失败与语义失败区分，再针对非确定性进行有限重试和单独统计。对于试图删测试、跳过断言或无条件吞异常的补丁，网关和检查规则需要阻止它绕开任务目标。判定标准必须固定，不能在看到模型输出后再修改规范，让结果显得更好。

相关工作方面，SWE-agent 已经提供代码操作闭环，EvalPlus 表明少量测试可能漏掉错误，近期还有修复与复现测试协同生成的研究。因此，我的候选项目不能以“会生成测试”为新贡献。真正准备比较的是测试机会怎样分配：在同一个候选池、相同公开信息和预算下，分歧驱动输入选择是否优于随机选择、规范边界枚举和单纯的模型置信度。共享候选池可以把补丁生成质量与选择策略的影响尽量分开。

数据准备从公开规范参照和自写小模块出发，构造有解释的受控缺陷，并按原始母题和缺陷变换划分开发、封存集合。如果把函数生成数据改造成修复任务，就必须说明这是派生集合，不能称为原始基准成绩。除了共享候选池实验，我还会做少量端到端检查，并把生成候选的费用也算进去。否则，一个选择器表面上很便宜，可能只是因为最昂贵的候选生成被排除在统计之外。

评价重点是完整修复率，而不是通过了多少可见测试。同时观察错误补丁接受率、引入回归、测试效率与调用费用，并展示合法极端输入上的表现。如果分歧选择只能在某几类边界错误上有效，我会限定结论，不把它外推成真实大仓库修复能力。这个项目最终应该让我能够解释一次补丁为什么被选择、哪些证据还不足，以及如何设计不让模型钻空子的评测。在实验完成前，所有成功率和改进幅度都必须保持为待测，而不是提前写进简历。

### 五组追问与参考回答

**追问 1：把所有测试都运行一遍，不比 Agent 挑测试更可靠吗？**

如果测试集合完整且运行便宜，全部运行很合理。我考虑的是测试输入空间很大、每次候选验证有成本的情况，需要决定新增测试测什么。Agent 用于理解规范和根据执行结果调整验证方向，但现有完整回归测试仍应运行，不能为了体现主动选择而故意省略必要检查。

**追问 2：这和已有的测试驱动修复有什么不同？**

测试驱动修复和协同生成已经存在。我拟验证的是相同候选池中的预算分配策略，即优先选择能暴露候选分歧的输入是否更有效。这个差异很有限，必须通过随机和规范边界基线验证；不能把整个自动修复方向归为自己的创新。

**追问 3：候选产生不同结果，你怎么知道哪个结果对？**

单靠分歧不知道。分歧只决定先查哪里，正确性需要独立规范判定器或已验证性质，再通过不可见的最终测试评估。如果没有可靠判定依据，系统就应该返回待人工判断，而不是按多数票把某个结果当成真值。

**追问 4：如何排除更好的补丁生成造成了提升？**

核心选择器实验共享固定的候选池，让各方案看到相同补丁和测试预算，再比较最终选择。之后补充端到端实验，并把候选生成成本算入。这样可以分别回答选择策略有没有用，以及整个系统是否划算，而不混淆两个结论。

**追问 5：你准备解决的工程难点是什么？**

主要是候选隔离、测试版本绑定和独立评分。每次结果必须对应明确的补丁版本，隐藏判定器不能泄漏，模型也不能修改测试规则。我计划实现这些执行和评测模块，第三方运行环境和模型注明来源；个人贡献最终用 `[本人实现部分]` 与具体提交证明。

### 两条简历描述草案

- 拟实现基于候选输出分歧的代码修复 Agent，结合受限编辑、隔离执行与独立性质检查，支持补丁选择证据回溯。
- 拟在按母题隔离的派生修复任务上比较随机、边界及主动测试策略；完成后填写 `[完整修复率]`、`[错误补丁接受率]` 与 `[总调用成本]`。

## T5 EvidenceTrail：主动反证检索的文献核查 Agent

对应理论与近邻：SciFact、ALCE、PaperQA2，以及引用验证器可靠性研究，见证据表 P18–P21。

### 三分钟项目介绍稿

老师好，我计划做一个能够主动寻找反证的文献核查 Agent。它关注的不是生成一篇很长的综述，而是核查一条具体主张。例如，某方法在某个任务和数据条件下是否优于对照。普通检索问答往往找到几段相关内容就开始回答，但相关不代表支持，引用真实存在也不代表文章说过这个结论。

我准备让系统先拆出主张中的对象、关系和适用条件，然后维护一份证据账本。每段证据要注明支持哪部分、是否包含限制条件、有没有与当前判断相冲突的信息。Agent 根据这些缺口决定继续查哪个方向，而不是每次都固定检索相同次数。

例如，系统找到一篇支持性能提升的摘要，但没有说明是否适用于小样本条件，那么下一步应围绕这个缺失条件检索。它也可以主动搜索反驳或限制性结果。如果证据始终不足，就返回证据不足，而不是为了让回答完整而补出一个结论。程序会检查引用编号、段落位置和原文一致性，模型则处理语义关系与搜索决策。

这个方向已有科学主张核查、引用评测和研究 Agent，甚至已有研究指出验证器本身也会出错。因此，我不会把带引用或会找反例当成创新。准备验证的是，按证据覆盖缺口安排搜索，能否在相同预算下，比固定检索和固定两轮正反搜索减少没有依据的断言。

实验准备使用固定开放语料和带人工标签的科学主张，避免实时搜索结果变化影响比较。不同方案共用同一个检索器和验证器，评价支持、反驳、证据不足三类结果，还要检查证据句是否正确，以及拒答是不是只是逃避困难任务。我也会人工复核一部分输出，不让模型互相打分成为唯一依据。

我认为这个题目能体现信息检索、证据管理、可靠性评估和停止策略。当前没有任何效果数字，而且自然语言证据的判断比较难。如果简单检索已经足够准确，Agent 可能只是增加成本，这个限制也需要在最后的实验和面试中如实解释。

### 八分钟深入讲述稿

老师好，我计划研究的是文献问答里的证据核查问题。很多系统能够返回一段流畅解释和几条看起来正式的引用，但里面其实有几个不同层次的问题：论文是否存在，原文是否包含被引用的内容，以及这段内容是否真的支持回答中的主张。前两项比较容易用程序检查，最后一项涉及语义和研究条件。如果把它们混在一起，就很容易用真实论文为错误结论提供表面的可信度。

我准备先把任务限制为单条主张核查。例如，一条主张认为某方法在指定任务和小样本条件下优于某个对照。系统先抽取对象、比较关系和条件，不急着给支持或反驳的标签。然后在固定文献语料中搜索，读取候选段落，为每条证据标注它覆盖了哪些部分。这样可以发现一种常见问题：检索到的论文确实讨论相同方法，却只在另一种数据规模或另一种指标下报告了结果。

Agent 的决策由证据缺口推动。如果主要对象已找到，但适用条件没有被覆盖，下一次搜索就应针对条件；如果找到一条支持材料，则可以检查有没有相反结果或明显的局限说明。这不是要求每个问题都机械地搜一次赞成、再搜一次反对，因为有些主张很简单，有些则需要反复澄清。模型要根据已经取得的证据决定下一个查询和读取动作，但总检索轮数与费用由程序限制。

证据账本会保存主张片段、文献和段落编号、原文、支持关系以及尚未解决的冲突。最终输出中每个重要判断都应能追溯到原文，而不能只引用另一个模型生成的摘要。相同论文的多个段落也不能被算成多个独立来源。如果多篇文章都转引同一项实验，需要注明它们在证据上的依赖，避免把重复引用误当成多次独立验证。来源可追溯并不保证结论正确，但它让错误能够被检查。

遇到冲突时，我准备先检查研究条件是否一致，而不是看到两个相反词语就判定论文相互矛盾。例如一个结果来自特定数据集，另一个来自不同设置，两者可能都成立。模型可以提出这种解释，但需要引用对应条件。若现有摘要不足以确认，就应标记证据不足，不能假装已经阅读了全文。最小版本只处理摘要和有限段落，所以它的结论范围也应该与能看到的材料保持一致。

验证器本身是另一个核心难点。一个模型说另一段回答有依据，并不能构成独立真值。系统可以用模型辅助判断语义蕴含，但要用人工标注检查它在否定、条件变化和证据缺失情况下会不会误判。程序负责引用位置和原文匹配这类确定性检查，语义质量则单独报告。近期研究已经讨论核查器的可靠性，所以我不会因为加入一个验证 Agent，就声称获得了事实正确性的保证。

工程结构准备分为语料索引、搜索工具、证据读取、覆盖账本、行动选择和最终核查。初版采用固定语料与普通倒排检索，减少实时搜索和付费服务带来的变化。文献内容只作为数据处理，其中即便出现指令文字，也不能改变系统的工具权限和判断规则。工具超时、检索为空和证据反驳需要分开记录。连续搜索没有新证据时应停止，并清楚说明当前结论为何仍不能成立。

相关工作方面，SciFact 提供了带证据的科学主张核查任务，ALCE 关注引用质量，PaperQA2 已经能进行文献搜索和矛盾发现。因此，我的拟议项目不能以这些功能作为新贡献。我想测量的是，按主张条件覆盖缺口决定继续搜索与停止，是否比固定轮数更有效。这个假设既可能提高证据完整性，也可能因拆解错误而把搜索引到错误方向，所以必须有取消反证和取消覆盖停止规则的消融。

实验计划在公开科学语料上进行，开发样本用来确定提示与停止规则，封存样本在规则固定后评价。不同方案共用语料、检索器、模型和验证器，不能只给新方法更好的召回工具。主指标是支持、反驳、证据不足三类的宏平均表现，同时看证据句是否正确、没有依据的断言比例、实际覆盖率和成本。拒答可以降低错误，但如果系统几乎什么都不回答，它也不能算成功，所以正确性必须和覆盖率一起呈现。

此外，我准备人工检查一部分按类别和冲突类型抽取的结果，分析自动评分与人工判断的分歧。如果只有我一名审阅者，就明确说明这一限制，不把它称为专家评审。公开科学基准也不能自动代表计算机领域的研究能力，若增加计算机论文演示，需要单独准备和核对资料。最终我希望能拿一条完整轨迹说明系统为什么继续查、为什么停止、为什么某条引用不足以支撑结论，而不是只展示一页看起来很专业的答案。

### 五组追问与参考回答

**追问 1：普通 RAG 已经会检索，为什么还需要 Agent？**

如果一次检索就覆盖所有关键条件，普通 RAG 可能更合适。Agent 的价值在于，根据已经找到的证据调整查询、补查缺口或停止。如果实验发现固定检索同样准确且成本更低，我会保留这个结论，不把动态搜索视为必须采用的架构。

**追问 2：PaperQA2 已经会找矛盾，你的创新是什么？**

矛盾发现不是我的新点。拟验证的是，在固定语料和预算内，以主张条件的证据覆盖缺口来安排搜索，是否比固定正反两轮更有效。这是窄范围机制改进，需要明确近邻和消融；如果只是在提示里加一句“找反证”，就不足以构成有深度的项目贡献。

**追问 3：怎么区分没有找到证据和主张是假的？**

二者不同。没有找到支持或反驳材料时，只能说当前证据不足，不能推出主张为假。判断反驳需要有与主张在相同适用范围内不相容的证据。我会把检索失败、条件不匹配和实际反驳分别记录，这也是使用三类标签的重要原因。

**追问 4：如何排除更强检索器或验证器带来的提升？**

各方案必须共用相同检索器、语料和核查器，主要改变搜索顺序与停止规则，并把模型调用总成本算在一起。同时检查人工金标与验证器的差异，避免把评判模型的偏好误认为系统进步。只用模型给自己打分是不够的。

**追问 5：最难的工程问题和个人贡献是什么？**

我认为是维护可回查的主张—段落对应关系，以及让检索、摘要和最终回答不丢失条件限定。我计划实现证据账本、工具接口、覆盖检查与评测流程，底层语言模型和公开数据明确引用。最终个人贡献填写 `[本人实现部分]`，效果用真实审阅和运行记录支持。
